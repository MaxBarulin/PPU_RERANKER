# Как устроена проверка ППУ: шпаргалка с ответами на вопросы

Сначала весь путь одного ППУ на одной странице, потом каждый участок
подробно, в конце вопросы, которые обычно задают, с готовыми ответами. Все
цифры взяты из кода сервиса, а не на глаз.

## Путь одного ППУ за 30 секунд

| № | Участок | Что делает | Где в коде |
|---|---|---|---|
| 1 | Склад | Загружает реестр, разбирает ППУ на название / проблему / решение, чистит текст, выписывает цех и участок | `ppu/loader.py`, `ppu/normalize.py` |
| 2 | Векторы | Переводит каждый текст в 1024 числа моделью bge-m3. Похожие по смыслу тексты дают близкие числа | `ppu/embed.py`, `ppu/index.py` |
| 3 | Поиск | Ищет двумя способами, по смыслу (векторы) и по словам (BM25), и сливает два списка в один по общему рейтингу | `ppu/search.py`, `ppu/lexical.py` |
| 4 | Быстрый вывод | Сравнивает близость с порогами: повтор / другое подразделение / та же проблема, другое решение / похоже / далеко | `ppu/assess.py` |
| 5 | Судья | По кнопке «Проверить подробнее» языковая модель Qwen читает тексты целиком и объясняет связь в нескольких словах | `ppu/judge.py`, `ppu/llm.py` |

Быстрая проверка (участки 1-4 для нового ППУ) занимает секунды. Подробная
(участок 5) идёт от десятков секунд до нескольких минут. Решение всегда
принимают люди, сервис только показывает, куда смотреть.

## Участок 1. Склад

- **Откуда данные.** Excel-выгрузка реестра загружается на странице `/admin`.
  Подключение напрямую к базе (MS SQL) готово в коде, но ждёт сетевого
  доступа от ИТ.
- **На какие части делится ППУ.** Название. Проблема = поле «До улучшения».
  Решение = «После улучшения» + «Предложения». Плюс «всё вместе». Проблему и
  решение сравниваем отдельно: та же проблема с другим решением - это не повтор,
  а «альтернатива».
- **Что чистится.** HTML-теги, заглушки «См.вложение» / «см. приложение»,
  сокращения («пр-ва» → «производства», «уч. 5» → «участок 5» и т.п.).
  Оригинальный текст не меняется, людям показывается он.
- **Место.** Отдельно выписываются номера цехов и участков. По ним сервис
  отличает повтор от «той же идеи в другом цехе» (тиражирование).
- **Записи «только название».** Если описания нет (только «См.вложение»), такая
  запись помечается, и для неё действуют более строгие пороги: сравнивать
  почти нечего.

## Участок 2. Векторы

- **Что такое вектор.** Это «адрес» текста на карте смыслов: 1024 числа.
  Похожие по смыслу тексты получают близкие адреса, даже если слова разные
  («треснули ручки напильников» и «разваливаются рукоятки инструмента»).
- **Кто считает.** Модель **bge-m3**. Она обучена на огромном количестве
  текстов на 100+ языках и работает на нашем сервере. Она не «понимает» текст
  как человек: она выучила, что слова в похожих ситуациях значат похожее.
- **Как мерим похожесть.** По углу между двумя векторами (косинус угла):
  1 - смысл совпадает, около 0 - не связаны.
- **Четыре вектора на ППУ.** Название, проблема, решение, всё вместе. На весь
  реестр (около 11 тыс. ППУ) это до ~44 тыс. векторов. Они считаются один раз
  и хранятся в кэше. При обновлении реестра считаются только новые и
  изменённые записи. Ключ кэша - сам текст, поэтому изменённый текст
  посчитается заново автоматически.

## Участок 3. Поиск

**По смыслу.** Новое ППУ переводится в те же 4 вектора. Общая близость к каждой
записи - взвешенная сумма: весь текст 40%, название 20%, проблема 20%,
решение 20%. Если у записи какой-то части нет, её вес делится между остальными.

**По словам (BM25).** Это классический поисковый алгоритм, только «умный»:

- слова приводятся к начальной форме (библиотека pymorphy3): «ручек», «ручкой»,
  «ручки» → «ручка»;
- служебные слова («и», «в», «на», «для», «который»…) отбрасываются;
- **редкие слова весят больше частых** (IDF). Слово, которое есть почти в
  каждом ППУ, почти ничего не значит, а редкое совпадение значит много;
- ловит то, что векторы размывают: марки оборудования, номера, точные термины.

**Слияние (RRF).** Получаются два списка с местами. Для каждой записи
считается `1/(60 + место по смыслу) + 1/(60 + место по словам)`. Кто высоко в
обоих списках, поднимается наверх. Этот рейтинг считается для всего реестра.

**Что видно в интерфейсе.**

- Основной список - найденные «похожие по смыслу» (всё, что не «далеко»).
  Если таких нет, показываются первые 3 по поиску, чтобы было с чего начать.
- «Показать ещё» - всё остальное найденное во всём реестре: записи, у которых
  есть общие слова или хоть какая-то близость. Сверху - самые близкие по
  смыслу и по словам (тот же общий рейтинг). Карточки подгружаются по 50,
  кнопкой внизу. В вывод они не входят.
- «Общие слова» - редкие слова, которые есть и в новом ППУ, и в найденном.
  Не показываются цифры, подписи «проблема / решение» и слова, которые есть
  больше чем в четверти реестра.
- «Во всей базе: «слово» - N ППУ» - сколько записей во **всём** реестре
  содержит это слово (не только среди найденных). По кнопке открывается их
  список.

## Участок 4. Быстрый вывод

**Связь каждого найденного ППУ** определяется по косинусу (общей близости по
смыслу) и порогам. Пороги по умолчанию, для записей с описанием:

| Близость (косинус) | Связь |
|---|---|
| ≥ 0,72 | повтор (или «другое подразделение», если цеха разные) |
| 0,65 - 0,72 | похоже |
| < 0,65 | далеко |
| проблемы ≥ 0,75, решения < 0,75, общая ≥ 0,65 | та же проблема, другое решение |
| 0,65 - 0,76 | серая зона: «Спорный случай», лучше проверить подробно |

Для записей «только название» пороги строже: повтор от 0,76, похоже от 0,62.

**Процент «близости» в карточке - это не сам косинус.** Это шкала, удобная
для глаза: 0% соответствует косинусу 0,55 и ниже, 100% - косинусу 0,80 и выше
(для «только название» - 0,84). Поэтому 24% означает косинус около 0,61: по
смыслу далековато, но не совсем мимо.

**Общий вывод** берётся по самому серьёзному совпадению среди найденных:
повтор → другое подразделение → та же проблема → похоже → «похожих не найдено».

**Уникальность.** В быстрой проверке это 100% минус близость ближайшего.
После подробной проверки она берётся по самой серьёзной связи, которую
назвал судья: повтор - 5%, другое подразделение - 10%, та же проблема с другим
решением - 40%, похоже - 65%, не связаны - 100%.

**Откуда пороги.** Пороги по умолчанию подобраны на синтетических
(придуманных) ППУ: на них порог 0,72 ловил 93% «той же идеи» и 0% ложных
срабатываний на новых. Чтобы пороги подходили именно нашему реестру, есть
**калибровка** (страница `/admin`):

1. Сервис выбирает пары «ППУ и его ближайший сосед» поровну из полос
   близости 0,55-0,60, 0,60-0,65 … 0,90-1,0. Иначе почти все пары были бы
   «далеко».
2. Люди размечают пары на странице `/label` (повтор / другое подразделение /
   та же проблема, другое решение / похоже / не связаны / непонятно). Это
   может сделать и судья, а люди потом проверяют его метки.
3. Сервис подбирает пороги так, чтобы его ответы лучше всего совпадали с
   разметкой людей. Порог «повтор» ставится по лучшему совпадению. Порог
   «похоже» - так, чтобы ниже него уходило не больше 5% настоящих повторов.
   Нужно хотя бы по 5 пар «та же идея» и «остальное».

## Участок 5. Судья

- **Что это.** Большая языковая модель (LLM) **Qwen**. Сначала её обучали
  на гигантской библиотеке текстов угадывать следующее слово. Чтобы делать
  это хорошо, модели пришлось уловить смысл, связи и логику текста. Потом её
  дообучили выполнять задания по инструкции. Так из «угадывателя слов»
  получается модель, которой можно дать задание эксперта.
- **Внимание (attention).** Главный механизм внутри. Обрабатывая каждое
  слово, модель смотрит на весь текст сразу и взвешивает, какие слова сейчас
  важны. Во фразе «ручки треснули, поэтому их заменили» она связывает «их» с
  «ручками». Поэтому судья сопоставляет проблему и решение нового ППУ с
  найденным, даже если они описаны разными словами и в разном порядке.
- **Размер и MoE.** 35 млрд параметров. Параметры - это настроечные числа,
  которые подбирались при обучении. Модель устроена как «смесь экспертов»
  (Mixture of Experts, MoE): внутри много отдельных блоков-«экспертов», и для
  каждого слова распределитель (router) выбирает несколько подходящих.
  Работает только около 3 млрд параметров (буквы A3B в названии модели).
  Поэтому большая модель отвечает достаточно быстро на нашем сервере.
- **Что получает.** Инструкцию «ты эксперт комиссии по ППУ на
  судостроительном заводе», определения связей, один разобранный пример,
  новое ППУ и до 4 найденных ППУ за раз. Тексты целиком, без обрезки.
  Проверяются все карточки основного списка (не «Показать ещё»).
- **Что отвечает.** Для каждого найденного - код (повтор / другое место /
  та же проблема, другое решение / похоже / не связаны / непонятно) и
  пояснение до 8 слов. Случайность выключена (temperature 0), поэтому на
  одни и те же тексты ответ повторяется.
- **Поправка по месту.** Если судья сказал «повтор», а сервис видит разные
  цеха, связь становится «другое подразделение»: номера цехов сервис
  извлекает надёжнее.
- **Ограничения.** Судья может ошибаться, особенно на записях «только
  название» (там он чаще говорит «непонятно»). Его ответ - подсказка, а не
  решение комиссии.

## Где это работает

- Сервер `srv-ai` в заводской сети. На нём три программы: веб-сервис
  (страница, поиск, пороги), сервер модели векторов bge-m3 и сервер судьи
  Qwen. Обе модели запущены через llama.cpp.
- Тексты ППУ не уходят за пределы предприятия, интернет для работы не нужен.
  Если когда-нибудь подключат внешний сервис для судьи, интерфейс прямо
  предупредит об этом под кнопкой.
- Страницы `/admin` (обновление базы, калибровка) и `/label` (разметка)
  закрыты паролем администратора. После 10 неверных попыток с одного адреса
  вход блокируется на 10 минут.
- Пока база пересобирается, проверка работает по старой базе.

## Вопросы, которые могут задать

**Это искусственный интеллект решает за комиссию?**
Нет. Быстрая проверка - это поиск и пороги, судья - подсказка с пояснением.
Сервис сужает поиск с 11 тысяч записей до нескольких карточек и показывает
почему. Решение - за людьми.

**Куда уходят наши данные?**
Никуда. Модели работают на сервере предприятия, сервису не нужен интернет.

**Почему близость 24%, а судья пишет «повтор»?**
Цифры мерят общий смысл текста, а судья читает по существу. В примере из
ролика новое ППУ - «форма проверки ППУ на дубликаты», найденное - «аналитика
ПС ППУ». Слова разные, близость невысокая, а задача общая: работа с данными
реестра ППУ. Поэтому есть кнопка «Проверить подробнее», и поэтому финальное
слово за комиссией: это может быть и повтор, и развитие идеи.

**Почему сверху «Похожих по смыслу нет», а вывод «Такое ППУ уже было»?**
Сводка сверху - результат быстрой проверки (по цифрам). Вывод после
подробной проверки учитывает мнение судьи.

**Почему не искать просто по словам?**
Одну и ту же проблему описывают разными словами. Поиск по словам находит
«ручки напильников», но пропускает «рукоятки инструмента». Векторы это
ловят. А поиск по словам оставлен для точных совпадений: марки, номера,
термины.

**Почему не только векторы?**
Векторы «размывают» точные детали: «SCV-400» и «SCV-500» для них могут
оказаться почти одинаковыми. Два поиска вместе надёжнее.

**Что такое «1024 числа»? Откуда они?**
Это координаты текста на карте смыслов, их выдаёт модель bge-m3. Каждое
отдельное число ничего не значит, смысл - в их сочетании. Близкие по смыслу
тексты получают близкие наборы чисел.

**Откуда взялись пороги? Не с потолка?**
По умолчанию - с синтетики (придуманных ППУ с известным ответом). Для нашего
реестра их подстраивает калибровка по разметке людей (см. участок 4).

**Сколько времени занимает проверка?**
Быстрая - секунды. Подробная - от десятков секунд до нескольких минут:
зависит от числа найденных карточек (по 4 за запрос) и загрузки сервера.

**Что если в реестре вместо описания «См.вложение»?**
Вложения сервис не читает. Такая запись сравнивается только по названию,
с более строгими порогами, а судья скорее скажет «непонятно».

**Сервис может пропустить повтор?**
Может, если повтор описан совсем другими словами и в другом ракурсе. Поэтому
есть «Показать ещё» (всё остальное найденное) и списки «все ППУ со словом» по
ключевым словам. Калибровка на нашей разметке уменьшает пропуски.

**Как обновляется база?**
Ответственный загружает свежий Excel на странице `/admin`, база
пересобирается (векторы считаются только для новых и изменённых записей).
Позже - напрямую из базы данных реестра.

**Что за модели и можно ли их поменять?**
bge-m3 (векторы) и Qwen (судья), обе открытые и работают локально через
llama.cpp. Адреса и имена моделей задаются в настройках сервера (`.env`), код
менять не нужно.
