# Проверка ППУ на повторы

Когда приходит новое предложение по улучшению (ППУ), система ищет в реестре
похожие и отвечает: такое уже было, такая идея уже была в другом
подразделении, эта проблема уже поднималась с другим решением, есть похожие
или похожих нет. К вердикту прилагаются найденные ППУ с их статусом,
экономическим эффектом и текстом.

Работает полностью локально: модели запускаются через llama.cpp, данные
никуда не уходят.

```
новое ППУ (наименование, до, после, предложения)
   │
   ├─ нормализация ── чистка «См.вложение», HTML, сокращений; цех/участок/проект
   │
   ├─ поиск кандидатов ── BM25 по леммам + векторы bge-m3, слияние RRF → топ-20
   │
   ├─ вердикт по векторам ── пороги отдельно для «есть описание» / «только название»,
   │                         проблема и решение сравниваются отдельно
   │
   └─ спорный случай? ── LLM-судья (qwen) читает ППУ и 4 кандидата
                          (в вебе — по кнопке, на CPU это до минуты)
```

## Как это работает — простыми словами

Разберём на живом примере. Приходит новое ППУ:

> **Подставка под ноги для сварщика.** До: у сварщиков устают ноги при работе
> сидя. Предложения: сварить подставку из обрезков уголка.

### Шаг 0. Заранее, один раз: индекс реестра

Чтобы не читать 11 600 ППУ при каждой проверке, реестр один раз
переводится в удобный для сравнения вид (`build-index.bat`).

**Чистка.** Убираем мусор: «См.вложение» вместо текста, HTML-теги,
раскрываем сокращения («пр-ва» → «производства», «уч 7500» → «участок 7500»).
Номера цехов, участков, проектов, марки оборудования вытаскиваются в
отдельное поле — пригодятся, чтобы отличить «повтор» от «то же в другом цехе».

**Векторы (смысл).** Модель bge-m3 превращает текст в 1024 числа — что-то вроде
координат смысла. Тексты об одном и том же оказываются рядом, даже если
написаны разными словами: «шумоизоляция вибростенда» и «звукоизоляция
круговой виброустановки» — соседи. Насколько рядом, меряется **близостью**
(косинусом): 1 — одно и то же, 0.7–0.8 — очень похоже, 0.4–0.5 — «оба текста
про завод». До нуля у этой модели не доходит никогда, поэтому пороги
выглядят непривычно высокими.

У каждой записи не один вектор, а четыре: **название**, **весь текст**,
**проблема** («До улучшения») и **решение** («После» + «Предложения»).
Зачем — станет ясно на шаге 3.

**Словарь (слова).** Параллельно строится обычный поиск по словам (BM25):
слова приводятся к начальной форме («подставки» → «подставка»), редкие
слова весят больше частых — «каплеструйный» говорит о тексте больше, чем
«работа».

Зачем два способа: векторы хорошо ловят смысл, но размывают точные вещи —
марку «SCV-400» или номер проекта. Поиск по словам — наоборот. Вместе они
теряют меньше.

### Шаг 1. Новое ППУ проходит ту же чистку

…и превращается в те же четыре вектора. Это доли секунды.

### Шаг 2. Поиск кандидатов

Новое ППУ сравнивается со **всеми** записями реестра — это одно умножение
матриц, миллисекунды. Получается два списка «самых похожих»: по смыслу и
по словам. Их склеивают (метод RRF): запись получает очки за место в
каждом списке, и наверх поднимаются те, кто высоко в обоих. Дальше идут
20 лучших.

Близость по смыслу считается как взвешенная сумма: весь текст — 40%,
название, проблема и решение — по 20%. Если у записи из реестра нет
описания (только название), сравнивается то, что есть.

В нашем примере наверху окажутся «Подставка для ног», «Подставка под ноги
на сварочном посту»… и «Подставка для руки сварщика».

### Шаг 3. Вердикт по векторам — пороги

Каждому кандидату по его близости присваивается связь:

| Условие | Связь |
|---|---|
| близость ≥ **same** | «та же идея»: если номера цехов в текстах разные — **другое подразделение**, иначе **повтор** |
| проблема похожа (≥ 0.75), а решение нет (< 0.75) | **та же проблема, другое решение** — вот зачем проблема и решение векторизуются отдельно |
| близость ≥ **similar** | **похоже** |
| ниже | далеко — не показывается |

Вердикт по ППУ — самая сильная связь среди кандидатов. **Уникальность** —
насколько далеко самый близкий (100% — рядом никого).

**Где векторы ошибаются.** Близость — одно число, и оно не понимает
мелочей, которые меняют суть. «Подставка для **руки** сварщика» и
«подставка для **ног** сварщика» для векторов почти одно и то же: те же
слова, та же тема, тот же пост. Поэтому вокруг порогов есть **серая зона**:
кандидаты в ней помечаются «не уверен», а вердикт — «спорный случай».

### Шаг 4. Спорный случай — читает LLM

Языковая модель (qwen) получает правила, короткий пример, новое ППУ и
4 верхних кандидата — и для каждого отвечает кодом связи и пояснением в
несколько слов. Она действительно *читает*: «другая проблема: усталость
руки» — и исправляет векторы. На проверке даже маленькая 4B-модель
развернула и «подставку для руки» (векторы: повтор → LLM: другое), и
настоящие «подставки для ног» (векторы: похоже → LLM: повтор).

Почему не всегда, раз она умнее: на рабочем CPU модель выдаёт ~10 токенов в
секунду, а промпт — ~700 токенов. Это десятки секунд на каждую проверку.
Поэтому сначала быстрый ответ векторов, а LLM — по кнопке, когда векторы
не уверены (или когда хочется перепроверить). Её можно отменить.

### Шаг 5. Откуда берутся пороги

Числа вроде «same = 0.72» — не магия. Сначала их подобрали на синтетике:
выдуманных ППУ, где заранее известно, что чему повтор. На реальном реестре
они промахиваются, поэтому есть **калибровка**: ты размечаешь пару сотен
реальных пар («это повтор», «это просто похоже»…), и программа подбирает
пороги так, чтобы вердикт по векторам совпадал с разметкой как можно
чаще — см. [Калибровка порогов](#калибровка-порогов-на-реальном-реестре).

Был ещё **реранкер** (bge-reranker) — модель, которая сравнивает пару
текстов напрямую. Проверка показала, что он отвечает на вопрос «про ту же
тему?», а не «та же идея?», и новые ППУ получали у него такие же оценки,
как повторы. Поэтому в вердикте он не участвует.

### Чего система не делает

- Не читает вложения: если весь текст во вложении, сравнивается одно название.
- Не знает, внедрено ли предложение на самом деле, — только статус из реестра.
- Не решает за комиссию: показывает похожие ППУ и свою оценку, решение — за людьми.

## Быстрый старт на работе

Нужно: Windows, Python 3.11+, собранный llama.cpp (`llama-server.exe`),
GGUF-файлы `bge-m3` и (для судьи) `Qwen3.6-35B-A3B`.

1. Установить зависимости — см. [Установка](#установка).
2. Скопировать `.env.example` в `.env`. Значения по умолчанию в нём уже для работы.
3. Поправить пути к llama.cpp и моделям в начале батников
   `scripts\windows\start-embeddings.bat` и `scripts\windows\start-judge.bat`.
4. Запустить `start-embeddings.bat` и оставить окно открытым.
5. Собрать индекс:
   ```
   scripts\windows\build-index.bat "D:\реестр\Реестр ППУ.xlsx"
   ```
   Первый раз на CPU это долго (11 000 записей — от десятков минут до пары
   часов). Можно прервать и запустить снова — уже посчитанное возьмётся из кэша.
6. По желанию запустить `start-judge.bat` — нужен для кнопки «Уточнить у LLM».
7. Запустить `scripts\windows\start-web.bat` и открыть http://127.0.0.1:8000.

## Модели и llama-server

| Сервер | Батник | Порт | Обязателен | Зачем |
|---|---|---|---|---|
| bge-m3 | `start-embeddings.bat` | 8081 | да | векторы для поиска и вердикта |
| Qwen3.6-35B-A3B | `start-judge.bat` | 8080 | нет | судья для спорных случаев |
| bge-reranker-v2-m3 | `start-reranker.bat` | 8082 | нет | только для перепроверки в `ppu.evaluate` |

В каждом батнике наверху блок настроек: путь к `llama-server.exe`, путь к
модели, `NGL` (0 — только CPU, 99 — всё на видеокарту), `THREADS` (число
физических ядер).

Что важно в параметрах и почему:

- **Эмбеддинги и реранкер:** `-c`, `-b` и `-ub` одинаковые (8192). Эти модели
  обрабатывают текст только целиком за один проход, и llama-server откажет,
  если текст не влезет в `-ub`. `--pooling cls` — так устроен bge-m3.
- **Судья:** `--reasoning off` — без этого qwen сначала «думает» сотни
  токенов, на 10 т/с это минуты (а если лимита ответа не хватит — вернёт
  пустоту; интерфейс тогда так и скажет). `-np 1` — один слот, чтобы
  постоянная часть промпта (правила, ~480 токенов) оставалась в кэше и не
  считалась заново. Qwen3.5/3.6 — гибридные модели, обычный кэш промпта у них
  не работает, но llama-server сохраняет «контрольные точки» и восстанавливает
  их — в логе это `restored context checkpoint`.

Проверить, что сервер жив: открыть `http://127.0.0.1:8081/health` → `{"status":"ok"}`.

> Индекс и запросы должны считаться **одной и той же** моделью эмбеддингов.
> Поменяли GGUF или сервер (например, polza → llama.cpp) — пересоберите индекс.

## Подготовка реестра и индекса

`build-index.bat` делает два шага; их можно запускать и по отдельности.

**1. Нормализация** — читает Excel, сама находит лист и строку заголовка по
названиям колонок (`Наименование`, `До улучшения`, `После улучшения`,
`Предложения`, плюс `Рег. №`, `Статус`, `ЭЭ`, даты — если есть).

```bat
venv\Scripts\python -m ppu.prepare "Реестр ППУ.xlsx" --out data\registry_clean.jsonl
```

Работает без моделей и сети. Печатает отчёт о данных — **его стоит прочитать
при первом запуске**:

- сколько записей с описанием и сколько «только название» (вместо текста «См.вложение»);
- группы ППУ с одинаковым названием без учёта места и дат;
- **кандидаты в сокращения** — частые «орг.», «пр-ва», аббревиатуры. Известные
  раскрываются словарём `ABBREVIATIONS` и `ACRONYMS` в `ppu/normalize.py`;
  незнакомые оттуда стоит дописать (например, что такое МСЧ, КГИ) и
  перезапустить сборку — это улучшает поиск.

**2. Индекс** — лемматизация для BM25 и эмбеддинги четырёх «представлений»
каждой записи: название, полный текст, проблема («До»), решение («После» + «Предложения»).

```bat
venv\Scripts\python -m ppu.index data\registry_clean.jsonl --out data\index
```

**Когда пересобирать:** после пополнения реестра — просто снова запустить
`build-index.bat` с новым файлом. Эмбеддинги старых записей возьмутся из кэша,
считаться будут только новые. После пересборки перезапустить веб.

## Веб-интерфейс

```bat
scripts\windows\start-web.bat
rem или
venv\Scripts\python -m ppu.web --host 127.0.0.1 --port 8000
```

Чтобы открыть коллегам по сети — `--host 0.0.0.0` (в батнике `HOST=0.0.0.0`),
адрес будет `http://<имя-или-IP-компьютера>:8000`. Внешних CDN в странице нет,
работает без интернета.

- Слева форма: наименование и три поля описания. `Ctrl+Enter` — проверить.
- Справа вердикт, шкала уникальности и найденные ППУ. Карточка раскрывается —
  там полный текст, результат, цех/участок/проект.
- «Не уверен» на карточке и «Спорный случай» у вердикта — векторы не уверены.
  Тогда появляется кнопка **«Уточнить у LLM»**: судья перечитает новое ППУ и
  верхних кандидатов; у карточек появится его пояснение. Кнопку можно нажать и
  при уверенном вердикте — векторы тоже ошибаются.
- Пока судья работает, рядом есть **«Отменить»**: запрос обрывается, и
  llama-server прекращает генерацию. Пока модель читает промпт (префилл),
  прервать её нельзя — она остановится на первом же токене ответа.
- Если LLM настроена на внешний сервис (не localhost), под кнопкой красным
  написано, куда уйдёт текст.

API (для интеграции):

```
POST /api/assess   {"name", "before", "after", "proposal"}  → вердикт по векторам (быстро)
POST /api/judge    то же                                     → + проверка LLM (медленно)
GET  /api/info                                               → размер индекса, есть ли LLM и локальная ли
обрыв соединения клиентом во время /api/judge                → генерация в LLM останавливается
```

## Командная строка

```bat
rem вердикт
venv\Scripts\python -m ppu.assess --name "Подставка для ног сварщика" --before "Устают ноги" --proposal "Сварить подставку"
venv\Scripts\python -m ppu.assess --json new_ppu.json --llm          & rem LLM для спорных
venv\Scripts\python -m ppu.assess --id 1234 --llm-always             & rem запись из реестра против остальных

rem только кандидаты с оценками BM25 и векторов
venv\Scripts\python -m ppu.search --name "..." --top 10
```

`new_ppu.json`: `{"name": "...", "before": "...", "after": "...", "proposal": "..."}`.
`--raw` выводит полный JSON.

## Как читать результат

| Вердикт | Значит |
|---|---|
| Такое ППУ уже было | та же проблема и то же решение |
| Такая идея уже была в другом подразделении | то же, но в другом цехе/участке (тиражирование) |
| Эта проблема уже поднималась, но с другим решением | проблема совпадает, решение другое |
| Есть похожие ППУ | та же область, но не повтор — стоит взглянуть |
| Похожих ППУ не найдено | ничего близкого |

- **Уникальность** — насколько далеко самое близкое ППУ (100% — ничего близкого).
  После проверки LLM считается по её вердикту.
- **Близость** на карточке — нормированный косинус bge-m3: около 70 и выше —
  уже очень близко.
- «Повтор» и «другое подразделение» различаются по номерам цехов/участков в
  тексте. Если в найденном ППУ место не указано — будет «повтор» с пометкой
  «место в найденном не указано».
- У записей «только название» (вместо описания «См.вложение») сравнивать почти
  нечего — там система осторожнее и чаще отдаёт решение LLM.

## Качество и калибровка

Пороги подобраны на синтетическом наборе: 80 выдуманных ППУ по 16 темам и
по 4 варианта к каждому с известной связью (дубль, другое подразделение,
альтернатива, похожее) + 16 «новых». 40% записей реестра урезаны до
«только название», как в старых записях.

| | Только векторы | + LLM на спорных |
|---|---|---|
| «Та же идея» опознана как повтор/тиражирование | 55% | 87% |
| …у записей с описанием | 93% | 100% |
| …у записей «только название» | 13% | 72% |
| «Та же идея» не пропущена (не «уникально») | 95% | 94% |
| «Та же проблема, другое решение» (с описанием) | 53% | 74% |
| Новые ППУ ошибочно названы повтором | 0% | 12% |
| LLM вызывается | — | 44% запросов |

Выводы, которые заложены в код:

- **Реранкер `bge-reranker-v2-m3` в вердикте не используется.** Он оценивает
  «про ту же тему», а не «та же идея»: новые ППУ получали у него почти те же
  оценки, что и дубли. Косинус bge-m3 разделяет заметно лучше.
- Проблема и решение сравниваются отдельно: у альтернатив похожа проблема,
  но не решение.
- Пороги — константы в начале `ppu/assess.py` с комментариями, откуда они взялись.

### Перепроверка на работе

Синтетика выдуманная, её можно перенести на работу (`data\synth`) и
прогнать на локальных моделях — это проверит пороги на рабочем bge-m3 и
замерит реальную скорость судьи:

```bat
venv\Scripts\python -m ppu.evaluate --data data\synth --rebuild --llm
```

В отчёте (`data\synth\eval_report.txt`): recall поиска, матрица «тип связи →
вердикт» до и после LLM, токены и время судьи.

### Калибровка порогов на реальном реестре

Пороги с синтетики на реальных данных промахиваются (пример: «подставку
для руки» векторы назвали повтором «подставки для ног», а настоящие повторы —
лишь «похоже»). Калибровка — три шага, всё локально, модели нужны только
для веба:

1. **Выбрать пары** — запись реестра и её ближайший сосед, поровну из полос
   близости 0.55…1.0 (иначе почти все пары были бы «далеко»):
   ```bat
   venv\Scripts\python -m ppu.calibrate sample
   ```
   По умолчанию 240 пар → `data\calib\pairs.jsonl`. Секунды, без моделей.
2. **Разметить** в вебе: http://127.0.0.1:8000/label (ссылка есть в шапке).
   Две ППУ рядом, клавиши: `1` повтор · `2` то же, другое подразделение ·
   `3` та же проблема, другое решение · `4` похоже · `5` не связаны ·
   `0` непонятно · `Backspace` назад. Близость не показывается, чтобы не
   подсказывать. Метки — в `data\calib\labels.jsonl`, можно прерываться,
   размечать вдвоём на одном сервере. 240 пар — примерно 40–60 минут.
3. **Подобрать пороги** и посмотреть, что изменится:
   ```bat
   venv\Scripts\python -m ppu.calibrate fit            & rem только отчёт
   venv\Scripts\python -m ppu.calibrate fit --write    & rem записать data\thresholds.json
   ```
   Отчёт (`data\calib\fit_report.txt`): близость по меткам и матрица
   «метка → связь по векторам» — для текущих порогов и подобранных.
   `data\thresholds.json` подхватывают веб (после перезапуска), CLI и оценка;
   удалите файл — вернутся пороги с синтетики.

Как подбирается: `same` — середина плато лучшего F1 «та же идея против
остального»; `similar` — ниже него остаётся ≤5% «той же идеи» (повторы не
уходят в «уникально»); выше `gray_hi` «та же идея» верна в ≥90% случаев —
там LLM не нужен; правило «альтернатива» — перебор по F1. Пороги для
записей «только название» не трогаются (у реального реестра их ~1%).

### Проверка на своём наборе запросов

Можно собрать и набор «запрос → исходное ППУ» в формате синтетики — папка
с двумя файлами:

- `registry.jsonl` — реестр после `ppu.prepare` (можно взять `data\registry_clean.jsonl`,
  убрав из него записи, которые пойдут запросами);
- `queries.jsonl` — по строке на запрос:
  `{"qid": "...", "label": "duplicate|other_place|alternative|related|novel", "target": "<рег. № исходного или null>", "name": "...", "before": "...", "after": "...", "proposal": "..."}`.

```bat
venv\Scripts\python -m ppu.evaluate --data data\real_eval --rebuild --llm
venv\Scripts\python -m ppu.evaluate --data data\real_eval --rerank-url http://127.0.0.1:8082/v1
```

Второй запуск заодно покажет, не ведёт ли себя реранкер на реальных данных
лучше, чем на синтетике.

### Синтетика заново

```bat
venv\Scripts\python -m ppu.synth --out data\synth --model qwen/qwen3-235b-a22b-2507
```

Нужна сильная модель без рассуждений (на polza — `qwen3-235b-a22b-2507`).
Ответы кэшируются в `data\synth\raw`, повторный запуск продолжает с места.

## Дома и на работе

|  | Дома | Работа |
|---|---|---|
| Эмбеддинги | llama-server, bge-m3 GGUF (или polza.ai `baai/bge-m3` для синтетики) | llama-server, bge-m3 GGUF |
| Судья | llama-server с небольшой моделью (проверено: Qwen3.5-4B, ~15 с на GPU) или polza.ai — **только для синтетики** | llama-server, `--reasoning off`, CPU ~10 т/с |
| Данные | пример, синтетика; реальный реестр — только с локальными моделями | реальный реестр |

Реальный реестр во внешние сервисы не отправляется: если судья смотрит на
polza, кнопка «Уточнить у LLM» отправит туда текст нового ППУ и до 4 записей
реестра. Переключение — только адреса в `.env`, код одинаковый.

Даже Qwen3.5-4B как судья исправляет типичные ошибки векторов (например,
«подставка для руки» против «подставки для ног»), но на работе стоит брать
35B — она точнее на тонких случаях.

## Ограничения и что дальше

- **Вложения не читаются.** У старых записей текст часто только во вложении
  («См.вложение»), иногда это картинка. Пока такие записи сравниваются по
  названию. Следующий шаг — извлекать текст из вложений (doc/pdf, OCR для
  картинок) и подставлять в описание.
- **Группировка базы по темам** (кластеризация + названия тем от LLM) — ещё не сделана.
- Пороги откалиброваны на синтетике; на реальных данных их стоит перепроверить.
- Судья иногда называет повтором то, что человек счёл бы «похожим», —
  поэтому у каждого его вердикта есть короткое пояснение.
